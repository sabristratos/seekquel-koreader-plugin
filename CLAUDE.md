## What it is, and every rule that governs it

**Cross-format resume is an offer, never a silent jump.** On book open, the add-on fetches the linked book before it sends the device position. If Seekquel is farther ahead, it asks before moving to the closest percentage in the local file. A decline is stored per file and per offered target, so it stays quiet until Seekquel advances again. The menu can ask manually. The position state keeps the real pages turned before either choice, and the server caps credit to that ground, so moving between a hardcover, audiobook or different edition never turns skipped pages into reading. A percentage is the only portable coordinate; an exact EPUB path from a different format does not exist.

`spec/resume.sh` runs while changing this flow. It holds the prompt before movement, the KOReader percentage event, the zero-credit jump, the follow-up push and the per-target decline.

`seekquel.koplugin`: the first-party plugin that pairs by device code, links each file to a catalogue book, and sends reading time, highlights, finished status **and everything the book file itself carries** (description, ISBN, language, subjects, length, table of contents) to the backend's `/koreader` surface. **It does not send covers, and must not be made to again**: decoding a cover out of the file killed KOReader outright on the tester's Samsung, twice on two different books, so 1.4.3 removed the path along with `Api:pushCover` and `Metadata:cover`. Covers only ever applied to a reader's own private book that had none; that is the app's job now. The built-in KOSync client covers *position only* with nothing installed; this is the rest. **AGPL-3.0 by necessity**: it loads into KOReader's own process, and Lua ships as source regardless. Eleven files, no build step; distribution is a GitHub release zip plus the topic `koreader-plugin`. GitHub Actions are absent because the account billing lock prevents jobs from starting; run `luacheck .` and the seven local harnesses, then create the release and upload the zip through the GitHub REST API. **There is no plugin browser, store or installer in KOReader and there never was**: verified against a real v2026.07.1 build: `PluginLoader` scans `plugins/` and the data dir at startup for `*.koplugin` directories, and its management screen offers enable, disable and delete only. The GitHub topic is a discovery convention for people, not something the app reads. **So the add-on updates itself** (`seekquel_updater.lua`, from 1.3.0; current 1.12.0): the reader taps it, it verifies every file before replacing anything, and it only ever downloads from the server address the device is already set to. Installing is still a one-time file copy; updating is not. See `backend/CLAUDE.md` § *The add-on replaces itself*. **A `require` at the top of any plugin file is a load-time dependency for the whole add-on, and `PluginLoader` answers a missing one by skipping the plugin entirely**: one warning in a log the reader cannot reach, no menu, no pairing screen, nothing to report. `ffi/archiver` landed in koreader-base on 2025-05-23 and first shipped in KOReader **v2025.08** (v2025.04 pins a base from 2025-02-26), so requiring it unguarded made the add-on absent on every older build, and an absent add-on never pairs, so no measurement of ours could ever count the readers it happened to. 1.7.1 guards the require with `pcall`, exposes `Updater.canInstall()`, refuses `install()` with `too_old`, and refuses in `installUpdate` **before** `whenOnline`, so a reader on an old build is told to copy the files across instead of turning on wifi and waiting out a download that cannot land; the menu item names that too rather than offering an update it cannot do. `spec/updater_noarchiver.lua` simulates the missing module and holds all of it. Found by a fork (joelstitch), not by us. **Check every new `require` against the oldest KOReader we mean to support and guard anything newer, because the device report carries no KOReader version**, so that question is answered by reading upstream history rather than by our own data. **This repo is public and its history was started fresh at the first release: every commit is the owner's, and nothing in it may carry AI attribution, an em dash, or an explanatory comment.** `emulator/` runs a real KOReader desktop build on a virtual screen over noVNC and is the *only* layer that catches a wrong assumption about KOReader's API; the `spec/` Lua harness stubs the framework from the plugin's own assumptions and so agrees with those mistakes. **1.10.0 puts the add-on's actions on a gesture, and does it through KOReader's own Dispatcher rather than by handling touch itself.** `onDispatcherRegisterActions` runs in `init()` and registers five: `seekquel_sync_now`, `seekquel_sync_status`, `seekquel_todays_reading`, `seekquel_resume`, and `seekquel_set_status`, the last a `category = "string"` whose `args`/`toggle` are built from `STATUSES` so the four statuses cannot drift from the menu's. The reader binds them in Gesture Manager or in a profile, and **nothing is bound by default**: a gesture the add-on claims is one it takes from the reader. `require("dispatcher")` is unguarded on purpose, `registerAction` being present in v2025.04 as well as the pinned v2026.07.1 and so older than the floor the `ffi/archiver` incident set. Verified in the emulator rather than assumed, which is what that layer is for: a probe plugin loading after ours asked the real `Dispatcher:getNameFromItem` for each key and got our five titles back, `seekquel_set_status` rendering as `Seekquel: set the book's status: Did not finish`, against `Unknown item` for a key nobody registered. **Every gesture handler answers, and none may do nothing.** A gesture carries no enabled state the way a menu item does, so the guards the menu expressed through `enabled` are obstacles the handler notifies instead: `bookObstacle()` for no book open, `linkObstacle()` for a file the catalogue has not placed, `syncObstacle()` adding the network on top. `blockedBy()` is the single place that turns an obstacle into a message. **And `syncNow` refuses a repeat within `MANUAL_SYNC_REPEAT_SECONDS` of the last completed manual run**: a blocking run swallows input for up to 20s and the queued duplicate lands the instant it ends, so one misread swipe bought a second full freeze. The window is measured from completion rather than from the start, because the start is not when the duplicate arrives; and `manual_sync_at` is stamped only by the completion callback, so a run that never completes (wifi-on-demand that never connects) leaves the guard open rather than stuck shut. `spec/gestures.sh` holds all of it. **Seven of the nine harnesses run while editing** (`spec/settings.sh`, `spec/position.sh`, `spec/stats.sh`, `spec/chapters.sh`, `spec/resume.sh`, `spec/recap.sh`, `spec/gestures.sh`): no server, no token, no pairing approval, a second between them. `settings.sh` covers the settings store's own logic, which is where the rules that are easy to get subtly wrong live. It earned its place immediately: it caught `clearTiming` keying on `os.time()`, which counts in whole seconds, so a slower call recorded during a report shared the timestamp it was checked against and was thrown away. Reasoning had passed that twice. Anything decidable on the device alone belongs there rather than in `run.lua`, which needs the stack up. **1.5.3 is the first release driven by production analytics rather than by the tester.** Three findings, and the shape of each is worth keeping. A `PUT /device` from a Kindle Paperwhite had been failing for eight days against a `varchar(16)` column the request validated at 32, costing five of twelve readers their device identity, settings, diagnostics *and* the timezone offset that reply carries; it was invisible because the diagnostics that would report it are written by the statement that fails, and because the plugin reads a 500 as a reachable server so it never surfaced anything (`backend/CLAUDE.md` § *KOReader sync*). 36 of 81 reading-time pushes in one day credited zero minutes, so the add-on now fingerprints the day set and skips a call that would send totals the server already holds. And the upload ceiling came down from 30s to 15s after a device reported a real 25s `POST /sessions`, thirty being six times the plugin's own frozen-screen threshold. **A reader clears the queue in batches now, and the app tells them it is there** (2026-08-24). Measured on production the same day: 62 files were waiting across six readers and none had been answered, and almost none of them were books: one queue was thirty-five saved blog posts sent as an EPUB each, another was manga chapters and a plugin README. Setting one aside was one tap per file and the only place the count appeared was inside the KOReader screen itself, where it was capped at fifty and counted files that were already settled. See `backend/CLAUDE.md` § *KOReader sync*. **1.5.5 is the second release driven by production analytics, and the defect it fixes is a shape worth remembering: a device that syncs everything and never says what it is.** `reportDevice` rode the book-open path alone, inside `whenOnline`: and on an e-ink reader wifi is off to save battery, so that moment passes with no connection and the reader turns the radio on afterwards. Everything else then syncs through `onNetworkConnected` and `onResume`: position, reading time, highlights, status. Measured 2026-08-31, **three devices were syncing and had never once reported**, one paired that morning; `integration_devices.name` is written at pairing, which is why they looked half-configured rather than silent. The reply to that one call carries the reader's timezone offset, the settings they changed in the app and the news that a newer add-on exists, so those readers file their reading by the e-reader's clock rather than their own day, ignore every setting pushed from the phone, and can never self-update. It now rides resume and network-connect too, interval-gated at an hour (`reportDeviceIfDue`) because both of those paths already make several blocking calls: never reporting is the defect, reporting on every reconnect would be a different one. `spec/settings.sh` earned its keep again on the same change: it caught `disconnect()` not clearing the new timestamp, so a re-paired device would have inherited the old one and stayed silent for an hour, landing straight back in the state being fixed. **In testing on a physical device since 2026-08-10** (one reader, on their own e-reader), which is where the first real defects came from: an unplaceable file used to be saved as a private book and shelved as reading, which announced it to the reader's followers under a filename: see `backend/CLAUDE.md` § *A file the catalog cannot place waits for the reader*. **The freeze is diagnosed and fixed in 1.4.1; a distinct crash may or may not exist.** Every call the plugin makes blocks the reader's drawing thread while it waits, and a KOReader bug-report log from the tester's Boox on 2026-08-11 caught the worst case: opening a book, `PUT /device` ran inside the window where KOReader inhibits input, took 16s, *failed anyway*, and the screen was dead for 21s. 1.4.1 moves that work off the open path (`scheduleOpeningSync`), reduces sleep to a position push with a 4s cap and defers the rest to resume, and backs off for 120s after a transport failure so one unreachable server stops costing one timeout per call. That Boox log contains no crash; a second log the same day, from a **Samsung Galaxy A73** on pre-1.4.1 code, contains two deaths. One is a native `SIGABRT` (`pthread_mutex_lock called on a destroyed mutex`, tid `hwuiTask1`) with no Lua frame: Android's own render thread, cause unknown. The other is ours: the app was backgrounded at `Pause`, the process vanished ~2s later **without reaching `Stop` or `SaveInstanceState`**, and on restart the plugin's own interruption tracking reported `previous run stopped during PUT /syncs/progress`. That is the old suspend path: a chain of blocking calls started while Android was tearing the process down: caught in the act. 1.4.1 closed it by making `onSuspend`/`onRequestSuspend` call `cancelScheduled()` and send nothing at all, with `onResume`/`onRequestResume` re-queuing the push and every deferred network task going through `scheduleTask` so it is cancellable. **Sending nothing went too far, and 1.4.4/1.4.5 walked it back deliberately**: the moment the reader leaves KOReader is the moment they open Seekquel, so a suspend that syncs nothing shows them a stale page. `leaveQuietly()` now runs the full push (position, reading time, highlights, status) on the way out, but only when already online and configured, under a 5s whole-run budget and a 2s per-request timeout (`Api.LEAVING_TIMEOUT`), and it skips the file-metadata step entirely. The cancellable-task discipline is unchanged; what changed is that the leaving path is now bounded rather than absent. Anything that does not fit the budget still goes on resume. **The 120s backoff and that leaving path then defeated each other, and 1.5.0 is the fix.** Sleeping an Android reader turns its Wi-Fi off, so a 2s leaving request usually failed, which armed the backoff: and `onResume`'s re-queued push was then skipped for the next two minutes along with everything else, so the tester slept the device, woke it, and nothing had moved (reported 2026-08-12, and the exact symptom "when the device sleeps, the book doesn't sync"). `resumeSyncing()` and `onNetworkConnected` now call `Api:clearBackoff()` first: the backoff is an answer to "is this server reachable", and waking up or joining a network is precisely the event that invalidates it. Do not remove the backoff itself: it is what stops one dead server costing one timeout per call: and do not clear it anywhere else, since clearing it on a page turn would restore the per-call timeout storm it exists to prevent. **The order of a sync run is a priority order, not an arbitrary one.** `pushNow` sends position, then highlights, then reading time, then status: and the leaving path allows 5s for the whole run against a 2s per-request timeout, so whatever is third is what gets dropped. Highlights were last until 2026-08-12, which is why the tester highlighted a line, switched away, and watched Sync status report one still to send: a `sessions.ingested` at 11:48 UTC that same day shows `minutes_credited: 0`, i.e. the reading-time call routinely spends one of the three slots crediting nothing while sitting in front of the reader's own writing. Reading time is a per-day total the device dates itself, so it is complete whenever it lands; a passage is not. **But a fixed order against a fixed budget starves whatever is last, and on a slow enough device "complete whenever it lands" resolves to never.** Reader 671's Boox measured a 16s `GET /documents/{digest}` against `SYNC_BUDGET_SECONDS = 20`, so every run spent the budget on the calls ahead of reading time: position and highlights kept arriving daily while the book sat 90 pages in with 3 pages and 1 minute credited against it, and the device's own `last_sync_ok: false` had been saying so for two days before the reader reported it. 1.5.4 records which upload the budget cut off (`upload_deferred`, per book, in `PER_BOOK_KEYS`) and promotes it to the front of the next run, so the two take turns and neither can starve. Do not answer a starved-upload report by raising `SYNC_BUDGET_SECONDS`: 20s is already a blocked screen, and the fix for starvation is fairness, not more time. **The other half was that nothing retried**: `scheduleOpeningSync` sent position only, so a dropped passage waited for 20 page turns, a book close, a network change or a manual sync. It now calls `pushNow()` when `hasUnsyncedWork()` says there is something. Do not fix a dropped-work report by raising `LEAVING_BUDGET_SECONDS`; that is the number 1.4.1 exists to keep small. **1.5.6 is the third release driven by production analytics, it is reader 671 again, and the defect is the one this workspace has a standing rule about: a device that cannot answer and a device with nothing to say gave the same answer.** `Stats:daysFor` returned `{}` both when KOReader's `statistics.sqlite3` could not be opened or queried and when it opened fine and held no reading, so `sendReadingTime` returned success on `#days == 0`, `sent` stayed true, and the device reported `last_sync_ok: true`. A reader whose statistics stop recording is then indistinguishable from one who has not opened a book, on the device's Sync status screen (which spoke only when reading time was *waiting*) and in the diagnostics alike. Measured 2026-09-01: 671's last `sessions.ingested` was 2026-08-29 06:17 while position and highlights arrived daily for five days, their reader logged 3 pages and 117 seconds against a day they turned 68 pages, and they gave up and typed 85 minutes into the app by hand. That hand entry is how it was found: it raised `device_seconds` through `UpdateReadingActivity::adjust(device: true)` without stamping `sessions_synced_at` or logging `sessions.ingested`, which no ingest path can do. Population at the time was 3.3% of `reading_logs` day-rows over 14 days with no minutes, seven of eight affected readers holding exactly one such day against 671's four of eleven, so read a single timeless day as today-in-progress and a run of them as this. `Stats` now returns `ok`/`unreadable`/`untracked` beside the days, `unsentReadingDays` returns a state for all seven of its outcomes (adding `disabled`, `none`, `sent`, `refused`, `waiting`), `readingTimeLine` names every one of them on Sync status, and the last observed state rides the hourly device report as `diagnostics.reading_time`, which `reportDeviceHealth` logs as `device.reading_time_blocked` for the three that are faults rather than the reader's own switch. **`sent` is the state 671 was actually in, which is why the state alone is not enough**: their last successful send covered everything KOReader had recorded, so the honest answer was "up to date" and the problem was that KOReader had recorded nothing for three days. `diagnostics.reading_time_recorded` carries the newest day the device's statistics hold, and the Sync status line names it, so `sent` against a stale date reads as the defect it is. `spec/stats.sh` is new and holds exactly this distinction against a real SQLite. **Do not express a failed statistics read by setting `last_sync_ok` false**: that field answers "was the server reachable", and overloading it sends the next investigation after the network instead of after the device. **And do not enumerate `diagnostics.reading_time` with an `in:` rule** for the reason the `varchar(16)` incident already taught, a value a newer add-on invents must not 422 the whole report and take the reader's settings, timezone offset and update notice with it. **1.5.1 stops the add-on reporting a position the reader is merely looking at**, which is the second defect a real reader found: consulting the index at the back of a book 7% in recorded them at 94%, billed the leap to that day as pages read, announced three quarters of a book to their followers, and left the read-through's furthest mark at the index so everything they read afterwards counted for nothing (reported 2026-08-12). `seekquel_position.lua` is a pure state machine, specced by `spec/position.sh` with no stack up: a forward leap of more than about three pages becomes a *visit* that reports nothing until three page turns confirm it, a backward jump is always accepted since it can credit nothing, and the fraction of the book crossed a page at a time rides along as `covered` so the server can cap a day's credit at what was actually turned. The tolerance is derived from the file's own page count, so it means three pages in a hundred-page book and three in a thousand-page one. Three properties are each load-bearing and each closes a way the rule could be defeated. **A confirming turn must be movement**, never any event inside the tolerance band: a redraw reports the same position, and KOReader broadcasts one on a rotation, a font change or a dictionary closing, so counting those would let a reader sitting in the index confirm it without turning a page. **`covered` is clamped to one book on the way out**, because the server validates it as a fraction and rejects anything above 1 with a 422: which arms no backoff, so an unclamped total accumulated through a long outage would fail every push from then on and stop syncing entirely. **The anchor is settled at the opening sync rather than seeded at `onReaderReady`** (`Position:settle`): whether KOReader has restored the file's saved position by the time it broadcasts `ReaderReady` is exactly the sort of assumption the stub harness agrees with and only the emulator can check, and getting it wrong would have the add-on report the front of the book and hold the real position as an unconfirmed jump. Do not fold this back into `currentPosition()`: the raw sampler stays the raw sampler, and everything that reports a position reads the confirmed anchor instead. The server holds an unconfirmed leap of its own for the devices that have no such rule: see `backend/CLAUDE.md` § *KOReader sync*. **1.5.0 also syncs on a timer** (`scheduleIntervalSync`, 15 minutes by default, settable to 5/30/60/off from the device menu or from the app, which is what made `KoreaderDeviceSetting` carry a non-boolean case): page turns were the only in-book trigger, so a slow reader, or one who reads five pages and puts the book down without closing it, sent nothing until they next opened it. It reschedules itself and replaces its own pending run rather than adding one, so two open books cannot leave two timers alive; it answers to `auto_sync` like the page count does; and `unsyncedBatch()` gates each tick on pages turned, unsent passages or unsent reading time: the third added in 1.5.4, without which no tick ever fired *for* reading time and a batch the budget had dropped waited on unrelated work to come along: all three answerable on the device, because a tick that syncs nothing is still a blocked screen. **It returns the batch rather than a boolean, and that is load-bearing twice over.** It reads the stats DB to decide, and the caller then hands what it found to `pushNow` instead of having it recomputed a second time inside the run budget; and the reading-time half is gated on `isLinked()`, because `pushNow` bails at `refreshLink` before any upload, so waking the timer for a file the catalogue cannot place would poll a `GET /documents` every tick for as long as the reader left it open. A batch the server *refuses* is held in `history_refused` for the same reason: a 4xx arms no backoff and re-sending identical bytes cannot succeed, so without it one bad day polls forever. `onCloseDocument` still flushes synchronously and deliberately: the app is in the foreground there, and unlike Hardcover we accumulate rather than sync continuously, so a book that closes without flushing may not reopen for weeks. The Boox log also showed the tester runs five other add-ons, two of them throwing in the same session (`hardcoverapp`, `simpleui`); rule those out before assuming a Lua-level crash is ours. Ask for Menu → Help → Report a bug: on Android the logs live in memory and that is the only way off the device. The tester's devices are both **Android** (`gocolor7`, a Boox Go Color 7, and `i2405i`). **Android is also why sleeping the reader synced nothing until 1.3.1**: KOReader broadcasts `RequestSuspend` there and `Suspend` on a Kobo or Kindle, and the add-on only listened for the second. Treat "verified on a Kobo" as saying nothing about an Android reader, and vice versa. **Reading statistics are saved before they are read** (`flushStatistics`, unreleased): KOReader's statistics plugin buffers page turns in memory and writes `statistics.sqlite3` only every fifty turns (`MAX_PAGETURNS_BEFORE_FLUSH`), on close, on sleep and on a settings save, so a manual sync mid-sitting read a database up to 49 pages behind and Today's reading showed a stale day under "As of your last page turn" (reported 2026-09-20). `readingDays` now calls `ui.statistics:insertDB()` first, behind a type check and `pcall`, because a reader can switch the statistics plugin off; `insertDB` is present on v2025.04 as well as master, so it clears the `require` floor rule above. **Finished travels back, and only finished** (`applyFinishedStatus`, unreleased). The book-open `GET /documents/{digest}` the add-on already makes carries `book.status_changed_at` (server epoch seconds), and `status_mark` (per book, in `PER_BOOK_KEYS`) holds that value as of the device's own last status report: stamped from the response of every successful `setStatus`, automatic or from the menu. The add-on calls `ui.status:markBook(true)` only when all of these hold: Seekquel says `read`, its change is newer than the mark (server clock against server clock, never the device's), the device's current status equals the last one it reported (an unsent change on the device is newer and wins), and the device is not already complete. **A first sight only records the mark and writes nothing**, so upgrading devices and freshly linked files never mark an old finish, and re-reading a book finished earlier cannot flip it. The write is then recorded as seen (`markStatus`) so `sendStatusChange` never sends it back. `markBook(true)` is KOReader's own "mark as finished" on v2025.04 and master (it moves reading or abandoned to complete and never the reverse), which is why it is used rather than writing `summary.status`: master also updates the file browser's cache there. Nothing else ever travels back; a Seekquel `reading`, `did_not_finish` or `want_to_read` is deliberately not applied, because on an e-reader those are guesses about a file the reader has in their hands.
